# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)

## เปรียบเทียบ a กับ b

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario มั้ย | ไม่แตะตัวเลขจริงเลย ตอบแบบกว้างๆ ลอยๆ แล้วโยนตัวเลขพวกนี้ไปอยู่ใน Open questions หมด | หยิบตัวเลขมาคิดครบ ทั้ง p95 ต้องไม่เกิน 500ms, โหลดพีกช่วง 11.11 ที่ 200 req/s, แล้วก็ MailFast ที่ส่งได้แค่ 50 เมล/วิ |
| ทางเลือกที่พิจารณา | 1. เรียกตรงๆ (Synchronous) 2. ใช้ Message Queue แบบกว้างๆ 3. ทำ Background Worker ในหน่วยความจำ | 1. ยิง Goroutine ใน memory 2. RabbitMQ ติดตั้งเองบน K8s 3. Apache Kafka |
| จัดการแต้มสะสมแบบ ครั้งเดียวเท่านั้น และ rate limit ของ MailFast หรือไม่เพราะอะไร | ไม่ได้บอกวิธีชัดเจน แค่บอกให้คิวไปจัดการต่อ | ใช้คิวของ RabbitMQ มาเป็น buffer ช่วยอั้นโหลดไม่ให้ยิงเกิน 50 request/วินาที ส่วนแต้มสะสมให้ใช้ order_id เช็คความซ้ำซ้อน เพื่อไม่ให้แจกแต้มจนแต้มมัน double |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ | ไปแนะนำพวก Kafka หรือระบบคลาวด์ ทั้งๆ ที่ยังไม่รู้เลยว่าทีมทำเป็นไหม | ไม่มีอะไรที่คิดขึ้นมา อิงตามที่โจทย์บอกว่าทีมมี 4 คนและมี 2 คนเคยเล่น RabbitMQ มาก่อน แถมอยากได้แบบ open-source รันบน K8s เอง |

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | เพิ่ม Outbox Pattern หรือทำ local buffer ใส่ใน checkoutservice | เพื่อป้องกันกรณีตัดบัตรเครดิตผ่านแล้ว แต่จังหวะส่ง event เข้า RabbitMQ ดันพังหรือ pod ดับก่อน ข้อมูลจะได้ไม่หาย |
| 2 | แยกคิวกับ worker ของแต้มสะสม ออกจากคิวส่งเมลของ MailFast ให้ขาดจากกัน | เพราะระบบอีเมลมันติด rate limit 50 เมล/s เดี๋ยวคิวจะยาวจนทำให้แต้มสะสมได้ช้าเกิน 1 นาทีตาม SLA ที่ตั้งไว้ |
| 3 | ใส่ DLQ ให้ฝั่ง MailFast | MailFast มีโอกาสส่งพลาดประมาณ 0.5% ต้องมีคิวพักไว้ให้ทีมเข้าไปเช็คหรือสั่ง retry ย้อนหลังได้ |
